## 1. 缺陷认定

| 项 | 内容 |
|---|---|
| **现象** | 同一份清单中，配套文件行写 **186**、总览标题写 **188**、验收行写 **188**，而 14 个分类数字相加为 **187** |
| **根因** | 清单中的**文件数与字节数曾是手工维护的正文文本**。在结题轮内文件集合持续增长（新增了结题决策、主张登记、复现手册、验收证据等），而手工数字只在部分位置被同步更新 |
| **缺陷类别** | 与 **D43** 同类：**派生数值被手工固化，未由唯一事实源生成** |
| **影响面** | **仅影响交付清单的计数与字节数陈述**。不涉及任何科学数据、统计结果、账本、实验或结论 |
| **严重性** | **MAJOR（诚实性/可核验性）**：交付清单是外部审阅者最先阅读的文件，其自相矛盾会直接损害可核验性 |

## 3. 修复措施（根治而非改数字）

1. **计数改为生成**：`scripts/build_final_manifest.py` 现在输出一个生成区块
   （`<!-- BEGIN:GENERATED-COUNTS -->` … `<!-- END:GENERATED-COUNTS -->`），
   直接写入 `docs/FINAL_DELIVERY_MANIFEST.md` §1，并另存
   `docs/FINAL_ARTIFACT_COUNTS.md`。**正文不再手工维护任何计数。**
2. **新增 `--check` 校验模式**（EXIT 非 0 即失败），逐项校验：
   - 清单中**每一处**「N 个文件」声明 == CSV 行数；
   - 清单中**每一处**「N 字节」声明 == CSV 字节合计；
   - **分类表算术合计** == CSV 行数；
   - **关键哈希表**中每一行的 16 位前缀 == 该文件在 CSV 中的 SHA-256 前缀，
     且该路径**确实存在于 CSV**（防止出现"幽灵条目"）。
3. **消除其他位置的固化计数**：把 `docs/AUTONOMOUS_PROGRESS.md`、`docs/FINAL_DELIVERY.md`、
   `docs/LATEST_HANDOFF.md` 中写死的「187 个文件」改为**指向 CSV**，使其不再可能过期。
4. **生成器不自引用**：CSV、清单本身、计数摘要三者**排除在哈希集合之外**，避免鸡生蛋问题。

## 4. 校验强度验证（反向控制）

为避免"校验永远通过"的假安全感，做了 4 项**注入式反向控制**，全部被正确检出（EXIT 1）：

| # | 注入的错误 | 检出信息 |
|---|---|---|
| 1 | 把生成区块的合计从 `188` 改为 `187` | `manifest says 187 个文件; CSV total is 188` |
| 2 | 把某个分类数字改小（分类和不等于总数） | `category table sums to N; CSV total is 188` |
| 3 | 把关键哈希表某一行的哈希改为 `deadbeefdeadbeef` | `key-hash table <path>: deadbeef… but CSV has c631b107…` |
| 4 | 在关键哈希表中加入一个 CSV 里不存在的"幽灵文件" | `key-hash table lists 'nope/ghost.md' which is not in the CSV` |

**结论**：该校验不是形式化的"绿灯"，而是一个**会真正失败的闸门**。

## 6. 对我们的教训（已写入项目记忆）

> **交付文档里的任何"派生数值"都不得手工维护。**
> 计数、字节数、哈希、比例、表格小计——凡是由文件集合或数据**推导**出来的，
> 都必须由脚本生成，并配备一个**会失败的**一致性校验。
> 手写数字在后续编辑中**必然**漂移；这正是本轮审阅发现的缺陷，也是 D43 的同一类错误
> （把可由事实源推导的东西固化成了文本）。
